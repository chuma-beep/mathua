# ADR-061: One linear algebra engine, drawn in SVG, with elimination kept outside it

*2026-11-19*

**A 2×2 matrix acting on a plane is one engine, not six figures.** The prototype measured here shares a framework-free core (`prototypes/linalg.ts`: `mat`, `apply`, `compose`, `det`, `trace`, `inverse`, `eigen`, presets) across a transformation view, a column-combination view, a determinant view, an eigen view and an inverse view, and the whole prototype page compiles to **13,703 bytes of JavaScript, 4,649 bytes gzip**. The arithmetic is independent of React and of SVG: a full pass of `apply` + `det` + `inverse` + `eigen` costs **0.0001 ms** in Node over 100,000 iterations, which is five orders of magnitude below a frame at 60 Hz. That number matters because it removes rendering cost from the design question: at these sizes the engine is never the reason a figure feels slow, so the decision can be made on clarity, accessibility and maintenance instead.

**SVG is the renderer, and the existing visualisation surface is the reason.** Mathua already ships twenty-two figures as SVG through `FigureFrame`, `Axis`, `scale` and the theme tokens; a canvas or WebGL surface for a 2×2 matrix would add a second rendering model, a second accessibility story and a second coordinate system to debug, for a figure whose largest object is a grid of eighteen lines and a handful of arrows. Text in SVG is text: `Ae₁`, `det A` and `λ = 2` inherit the mono face, follow light and dark mode through `currentColor` and the `var(--accent-*)` tokens, and are readable by a screen reader. Three.js is not considered: the previous ADR justified it for a solid of revolution, where depth and lighting carry the mathematics, and none of that applies to a linear map of the plane. Canvas was rejected for the same reason the 3D ADR rejected it for 2D: a redraw loop and device-pixel-ratio arithmetic buy nothing at this element count.

**The mathematical core stays framework-free because the alternative has already failed in this repository.** The twenty-figure review found defects that a successful build could not see, including a determinant figure that rounded a small determinant to `0` beside coordinates that existed and a conic figure that called two parallel lines a parabola. Every one of those was arithmetic or classification, not rendering. A core with no imports can be tested against analytic values at a tolerance of `1e-9` — identity, zero, rotation, scaling, reflection, shear, projection, singular matrices, composition order, inversion, repeated eigenvalues, complex eigenvalues — and the same functions then feed every panel, so two views cannot disagree about what `Av` is. The prototype's test file already covers those cases in eleven tests, including a check that `compose(rotate, scale)` differs from `compose(scale, rotate)`, that a repeated eigenvalue does not invent two eigendirections, and that a quarter-turn reports `±i` rather than a real eigenline that does not exist.

**Production will extend `matrix.ts` rather than start a parallel module.** The existing module already owns `Vec2`, `Mat2`, `apply`, `mul`, `det`, `identity`, `rotation`, `reflection`, `dilation`, `compose`, `fromFlat`, `toFlat`, `dot`, `length`, `normalize`, `scaleVec`, `trace`, `angleBetween`, `addVec` and `subVec`. The additions the prototype proves are needed are `inverse` (with a relative singularity threshold), `eigen` (real, repeated and complex branches), and the small presets list. Creating a second matrix module would reproduce exactly the drift the review spent a session removing, so the engine lands where the operations already live, and the modal renderer becomes a template on top of it.

**Five views share the engine, and that is why it is worth being an engine.** A transformation view needs `apply` on grid lines, a combination view needs the two columns and the scalar multiples, a determinant view needs the unit square and `det`, an eigen view needs `eigen`, and an inverse view needs `inverse` plus `compose` to show the round trip. They share the same matrix state, the same presets and the same readout. The prototype varies all four entries and the vector in one place and every panel updates together, which is the property a collection of six independent components would not have had. The production shape follows from that: `MatrixTransform2D` gains a projection and shear preset, a column-combination readout and an inverse round-trip, `EigenDirections` gains the repeated and complex branches the prototype already classifies, and the existing `Transform2D` polygon figure is left alone because it teaches a transformation acting on a shape the learner built, which is a different lesson.

**Gaussian elimination is a separate module and a separate template.** A row operation is not a map of the plane: `R2 ← R2 − 3R1` changes a system into an equivalent one, and drawing it as arrows would claim a geometric relationship that does not exist. The prototype therefore keeps `prototypes/gauss.ts` with its own `eliminate(rows)` returning the reduced matrix, every elementary step with a description, and a classification of unique, infinitely many (with the free columns named) and none. It shares no code with the plane engine and imports nothing from it. The one thing the two have in common is the augmented-matrix display, and copying four lines of number formatting is cheaper than an abstraction that would only fit one caller.

**The prototype measured its own interface at three widths and found no overflow.** At 1280, 768 and 320 the page reports `document.scrollWidth − clientWidth = 0`, and the two-column layout collapses to a single column below `sm`, where the drawing is followed by the readout and then the controls rather than being squeezed beside them. Tab switches measured **19 ms on first paint and 31.6–32.5 ms afterwards**, which is two animation frames at 60 Hz rather than work: the handler and the React commit finish inside one frame, and the second frame is the measurement waiting for the next paint. The engine cost measured separately is 0.0001 ms, so the remaining cost is React re-render of a handful of SVG nodes. Mobile layouts prioritize readable controls over a single screen: the four matrix fields are full width in a two-column grid, the vector sliders span the row, and the readout stays a two-column `dl` at `text-[11px]`.

**Accessibility decisions carried from the existing frame.** Every value is reachable by keyboard: the four entries are native number inputs, the vector is two range inputs, presets are buttons, the view switcher is a `role="tab"` set with `aria-selected`, and the elimination panel exposes each cell as a labeled input with Back and Step buttons. The drawing is `role="img"` with an aria-label naming the view, the readout is a `<dl>` whose values are plain text, and nothing depends on color alone: orientation reversal is stated in words beside the signed determinant, and the complex eigenvalue case says `no real eigenvector` rather than drawing a rotation and leaving the reader to infer it. Reduced motion needs no handling because there is no animation loop; every view renders on demand from state.

**Known limitations, recorded rather than hidden.** The prototype's transformed grid is not clipped to the plot rectangle, so at large entries its lines cross the frame border, which the production template must fix with a clip path the way the existing matrix figure does. Eigenvectors are reported up to sign, which is inherent and must be said in the caption rather than presented as a unique direction. Complex eigenvalues are classified and printed but not drawn as a rotation of the plane, because a figure that drew them would need to explain the complex eigendirection, and that is a different lesson. `inverse` uses a relative threshold (`|det| ≤ 1e-10·max(1, |entry|)²`) rather than exact zero, so a genuinely singular matrix is caught while a merely small determinant is not called singular; the caption must not imply exact arithmetic. Elimination works on floating-point numbers, so a system whose pivot should be exactly zero may show `1e-17`; production should either round for display, as the prototype does, or move to exact rational arithmetic, which is a larger change than this ADR authorises. The prototype supports two equations in two unknowns; three-by-three needs a bigger panel and is not measured here.

**What this does not do.** It introduces no charting framework, no canvas, no WebGL, no 3D linear transformations and no dependency. It does not rewrite the existing matrix, eigen or polygon lessons, and it does not mark the linear-algebra topics complete: the coverage file moves only when the authored knowledge points and their figures pass the same audit as the other twenty-two, which is the rule the 3D and contour work followed. The prototype route itself is temporary and will be deleted once the production template carries the same six views, so there is one implementation rather than a demonstration beside it.

**Measurements are prototype measurements.** The numbers above were taken on a developer machine in Chromium at three viewport widths and in Node 24 for the engine loop. They establish order of magnitude and the absence of a rendering problem, not a production performance guarantee; a school laptop and a mid-range phone will be slower by an unknown factor, and the production chunk will differ from the prototype because it shares `FigureFrame`, `Controls` and the existing maths modules rather than carrying its own copy.
