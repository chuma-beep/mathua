# ADR-059: 3D solids use Three.js, lazily, inside the lesson flow

*2026-11-18*

**The decision is Three.js, loaded only by a step that draws a solid.** The numbers in this record measure a prototype on a developer machine; they are evidence for the choice, not a production performance guarantee. The proposal that opened this work listed 31 topics; 3D solids is one of the two still absent, and the earlier decision to defer it was a decision to defer a renderer choice, not to refuse 3D. Three candidate renderers were built against the same solid before this was written: a Three.js scene, a hand-rolled SVG projection and a Canvas 2D painter with a depth sort. All three draw the surface of revolution of r(x) = 1 + 0.35 sin(1.6x) about the x-axis on [0, 4], share one geometry module (`web/next-app/prototypes/solid.ts`), rotate by drag or arrow keys and move a cutting plane with a slider. The prototypes live in `web/next-app/prototypes/` behind an untracked dev route (`app/proto3d/page.tsx`), which is where the numbers below were measured.

**The measurements, and what they mean.** Built with `next build` and measured from the static export in `out/_next/static/chunks`, gzipped at level 9. Three.js: 488,913 bytes raw, **120,348 bytes compressed**, one chunk. Canvas 2D: 3,972 raw, 1,941 compressed, plus a shared geometry chunk of 3,908 raw and 1,714 compressed. SVG: 3,989 raw, 1,832 compressed, the same shared chunk. So Three.js costs roughly 100 KiB compressed more than either alternative, once, and only for a learner who opens a step that names a solid. Interaction cost, measured in headless Chromium with the CPU throttled 4× at a 900×900 viewport: twenty arrow-key turns took 11.0 ms each under Three.js, 31.6 ms under Canvas and 21.2 ms under SVG. First-frame cost from mode selection: **6.8 ms** for Three.js, 25.3 ms for Canvas, 277.0 ms for SVG, whose first paint projects about 1,900 points in JavaScript before anything appears. The two 2D options are cheap in bytes and expensive in work; Three.js is the reverse, which is the trade the user asked to have measured rather than assumed.

**Canvas loses on both axes, which rules it out.** It is 100 KiB lighter than Three.js and slower in interaction, because every turn re-projects 1,344 quads in JavaScript and fills them one by one; the browser's own compositor never sees a surface, only a finished bitmap. It also needs its own painter's sort, its own flat-shading model and its own cap handling, all of which exist in Three.js and none of which is mathematically interesting. A renderer that costs more code to maintain and produces a slower figure has no case, whatever its bundle.

**SVG survives as the fallback, and only as a fallback.** The wireframe is 1.8 KiB compressed and needs no WebGL, so it is the right answer when a context cannot be created, and it is what ships behind `webglAvailable()` in the prototype. It is not the right answer for the default: 277 ms to first paint is a visible stall on a phone, and a wireframe cannot shade a surface or hide the far side of one, so the learner has to reconstruct the solid from lines. The fallback draws the same geometry with the same controls and the same readout, so nothing is lost but the shading.

**Three.js also brings the things the later figures will need.** A 3D solids topic is not one figure: it is volumes of revolution, cross-sections, surfaces, rotations in space and the relationship between a solid and its shadow on each coordinate plane. A scene graph with a camera gives those for the price of new geometry, which is the part that is actually mathematics. The alternative is re-implementing perspective, depth sorting, lighting and picking for each new view, and the review that preceded this decision found twenty figures with twenty defects, so the surface area of hand-written rendering is the last place to add code.

**The cost is bounded, and the bound is verified rather than assumed.** The Three.js chunk is referenced by no HTML file in the export: `grep -rl` over `out/**/*.html` returns nothing for the chunk name, and `out/learn.html` references 54 chunks, none of them the renderer. The figure is mounted through the existing `VisualFigure` dispatcher, which already imports each template with `next/dynamic` and `ssr: false`, so the runtime arrives only when a step names `solid3d`, exactly as the eight-kilobyte tangent chunk does today. A learner who never opens a 3D step downloads none of it, and the main bundle is unchanged.

**It runs inside the lesson flow, not as an optional exploration mode.** The step is where the concept is introduced, the prediction block sits above the figure, and the readout carries the numbers the interaction produces; putting the solid behind a "try 3D" toggle would make the one figure that needs three dimensions an extra, and the append-only flow means a learner who never opens an optional mode never meets it. The figure is capped at the same 420px measure as the 2D figures and takes the same frame, title, reset, caption and live readout.

**Rendering is on demand, and nothing moves by itself.** The prototype calls `renderer.render` when the camera or the cutting plane changes, never in a `requestAnimationFrame` loop, which is why an idle figure costs nothing and why reduced motion needs no special case: there is no animation to suppress. Dragging rotates by pointer delta; the same rotation is available from the arrow keys with a visible focus ring, and the cross-section position is a native range input beside a numeric output, so every value the figure shows can be reached without a pointer. The canvas carries `role="img"` and an `aria-label`, and the numbers a screen reader needs are in the readout rather than in the pixels.

**The fallback is a capability check, not a browser sniff.** `webglAvailable()` tries to create a context once. If it fails, or if the renderer throws during construction, the dispatcher renders the SVG projection instead, with the same geometry and controls. This matters because the app is a static export used in locked-down environments where WebGL is disabled by policy, and a blank canvas is worse than a wireframe.

**Measured at a realistic phone width, the figure holds.** At 320px the prototype reports zero horizontal overflow, the canvas resizes with a `ResizeObserver`, and the interaction timings above were taken with the CPU throttled 4×, which is the closest a desktop headless browser gets to a mid-range phone. The honest limitation is that this is Chromium on a laptop with throttling, not a physical handset, and the 6.8 ms first frame benefits from the chunk being preloaded by the dev route; a first visit on a slow connection also pays the 117.5 KiB download.

**Maintenance is one wrapper and one geometry module.** The Three.js surface is a `BufferGeometry` built from a profile, a lambert material, one ambient light, one directional light and a camera on a spherical orbit; there is no control library, no post-processing and no physics. Upgrading Three.js is a dependency bump reviewed against the prototype route. The geometry module is plain arithmetic with unit tests, so a profile change is testable without a GPU, and the renderer is not imported by anything the unit suite loads, which keeps jsdom out of the problem. The figure's three.js version is pinned exactly, as the corpus pins its own tooling.

**What this does not do.** It adds no 3D figure to the curriculum yet, changes no existing template, and does not move the coverage counts: `coverage.json` is updated when a 3D step is authored, not when the renderer is chosen. It does not use `OrbitControls`, so touch and keyboard behavior stays ours to define. It does not animate a rotation or a sweep, because a learner-driven view is the claim this figure makes. And it leaves the shell-method and disk-method volume figures as 2D until a step names a solid.
