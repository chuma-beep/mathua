# ADR-058: An interactive visualization is declared data, and the browser owns its meaning

*2026-11-18*

**A knowledge-point shard names one template from a closed allowlist and supplies a small JSON parameters object. It does not point at a component, an image, a URL or code.** The shard is data, edited by whoever writes the curriculum. The curriculum is already 3015 lesson files plus 183 static diagrams that work this way. A figure that required a bespoke React component per concept would put the figure's existence behind a bundler entry and a build step that knows which lesson loads which file, and the first concept without a figure would need a placeholder to say so. The declared form is instead one optional field. `data/visualizations/types.json` lists six ids, `internal/lessons/visual.go` defines `Visual{Type, Title, Caption, Params json.RawMessage}`, and `lessons.KP` gained a single `Visual *Visual` field with `visual,omitempty`. A shard that names no visual is unchanged, which is 3009 of the 3015 lesson files.

**The server validates the envelope and refuses to interpret the payload.** It checks four things: the type appears on the allowlist, the title is at most 160 runes, the caption at most 600 and the parameters are a JSON object no larger than `MaxVisualParamsBytes = 8 * 1024`. It does not know what a matrix is. The alternative was a schema in Go mirroring each template's schema in TypeScript, which is two definitions of one fact and therefore the drift AGENTS.md §7 exists to prevent: the first template that gained an optional parameter would be accepted by the server and rejected by the browser, or the reverse, and neither side would be wrong in isolation. The browser already has to validate, because a figure must degrade quietly rather than throw inside a lesson, so the Zod object in `components/visual/schemas.ts` is the only definition of what a template accepts. The server's job is narrower and worth doing in Go: a shard cannot smuggle a data URL or an essay through a field the build reads on every start, and an unknown type is dropped with a logged warning before it ever reaches a client.

**The 8 KiB cap is a budget, not a security boundary.** The twelve authored payloads are between 60 and 220 bytes, so the cap sits roughly 40 times above the largest real one. It exists to catch the specific mistake of pasting a base64 image or a scraped dataset into a shard, which is a mistake someone will make once. It is checked as `len(params) > MaxVisualParamsBytes` after `bytes.TrimSpace`, and a parameter block that does not begin with `{` is rejected before the size check, so an array of a million zeros fails on shape rather than on arithmetic.

**Every figure is SVG for 2D, and Canvas and Three.js were evaluated rather than skipped.** SVG was chosen because the things this product needs from a figure are the things SVG hands over for free: text is text, so a `<text>` node is selectable, searchable and read by a screen reader; the drawing inherits `currentColor`, `var(--accent-blue)` and the theme tokens the rest of the app uses; and there is no redraw loop, so a figure costs nothing when the learner is reading the paragraph above it. Canvas would have meant a render loop, a device-pixel-ratio dance and text drawn as paths, for no gain at these element counts, the largest figure being 240 curve samples plus roughly 60 rectangles. Three.js is a different proposition and a real one for the 3D topics the proposal lists, but it is roughly an order of magnitude more code than a 2D figure, it needs a WebGL context per mounted figure, and it would have made eleven 2D concepts carry a 3D engine. The measured outcome is that the first tranche ships as 8.0K chunks, the later ones as 12K to 16K, and the main bundle contains no visualization code at all.

**Each template is its own chunk, loaded only when a step names it.** `components/visual/registry.ts` maps each id to a schema and a `load: () => import('./templates/...')`. A lesson with no visual downloads none of it; a lesson with the tangent figure downloads the tangent chunk and not the other five. The dispatcher is mounted through `next/dynamic` with `ssr: false` in `LearnStepper`, so the static export carries no visualization code into the HTML either. One consequence is worth recording because it is not obvious: the lazy component type must be stable across renders or React remounts the figure on every keystroke and the learner loses the value they were typing. `VisualFigure` therefore builds a module-level `LAZY_TEMPLATES` map once at import time and reads from it, and `eslint.config.mjs` turns off `react-hooks/static-components`, which cannot see through the lookup, alongside five React Compiler rules the repo already had off for the same reason of scope rather than disagreement.

**The figure cannot award XP, set mastery or move a review date, and that is structural rather than a promise.** No template performs a fetch. `FigureFrame` renders a title bar, a drawing, a `<dl aria-live="polite" data-testid="visual-readout">` and a caption, and nothing it renders is an input to any endpoint. The visual mounts inside the intro card of a knowledge point, after `KatexContent` renders the worked example and before the static assets and the concept diagram, and when a step carries a visual those static figures are suppressed so the learner is not shown the same idea twice. Reading the figure still awards nothing, exactly as reading the worked example awards nothing: a step advances when a question is answered, and that path is untouched. The verification for this is negative, which is the only kind that means anything here: no diff in the change touches `internal/xp`, `internal/scheduler`, `internal/engine` or the answer handlers, and the full suite, 1176 tests across 148 files, passes with the visualization mounted.

**Twenty-two templates are shipped: 27 of the proposal's 31 topics are complete, four are partial and none is absent.** Built and genuinely interactive: linear transformations, matrix multiplication as a geometric action, determinants as the area of the image square, eigenvectors and eigenvalues, vector addition and subtraction, scalar multiplication, basis and span, derivatives and tangent lines, instantaneous rates of change, Taylor series, limits and continuity, Riemann sums, integration as accumulated area, multivariable functions and their partial derivatives, geometric transformations, rotations and reflections, the Argand plane, modulus and argument, complex multiplication as rotation and scaling, complex functions and mappings, the geometric interpretation of analytic functions, polygons the learner constructs and then transforms, normal distributions, sampling distributions, regression and standard deviation. One figure sits outside the list: the elimination view teaches solving a linear system, which is a different activity from mapping the plane, so it is recorded under `supplementary` in the coverage file with that reason instead of inflating the topic count. Partially covered: coordinate geometry, where the workbench measures, halves and intersects but does not cover polar coordinates, circles or rotated conics; conic sections, where the figure classifies and draws the circle, ellipse, hyperbola and the degenerate pair of parallel lines, but a parabola needs a linear term this equation family does not have; and three-dimensional solids, where one solid of revolution is drawn in Three.js with a movable disk cross-section and an SVG wireframe fallback, but arbitrary surfaces, composed solids and 3D transformations are not shown; and contour visualisation, where the figure integrates five functions along four path families and draws the running value in a second plane, but its closed-path pole detection samples 4000 points and is therefore approximate, and residue theory, winding numbers and arbitrary expressions are not shown. **The canonical accounting is `data/visualizations/coverage.json`, one entry per proposal topic with its status and the templates that teach it.** `scripts/audit_visuals.py` fails when that file and the registry disagree, when an absent topic names a template, or when a template teaches no topic at all, so the counts in this paragraph are a quotation of that file rather than the owner of the number.

**The next template should be the 3D case, because it is the only remaining item that changes the architecture.** Complex contour visualisation fits the existing contract as it stands: a path, a field along it and an integral accumulated along the path are all two-dimensional data with two-dimensional drawing. Solids are different, since they are the one place where SVG stops being the right tool, so the decision to defer Three.js should be reopened when that template is specified rather than settled in advance. The optional second matrix on `MatrixTransform2D` is no longer owed: a shard may name `then` and `showBasis`, and the figure draws `A v` and then `B A v` against the composed matrix.

**One thing in the proposal is deliberately absent rather than forgotten.** Animation is not built: no figure moves by itself, which is also why reduced motion needs no special case beyond the loading skeleton. The proposal's fifth pedagogical step, asking the learner to predict before revealing, is built: a visual may carry an optional `Predict{Question, Options, Answer, Explain}`, the Go loader validates it, and `FigureFrame` renders a fieldset above the drawing with native radios and a `role="status"` reveal. It is authored content rather than generated, and it is never scored, stored or sent anywhere, because a prediction is a prompt and not evidence.

**Rejected alternatives, recorded so they are not re-proposed as new.** A component per concept, which would need a build-time map and would make the curriculum's data depend on the frontend's file layout. A Markdown image reference that names a template, which would put the figure inside a paragraph rather than in the step structure the stepper renders and would leave no place for a caption or a readout. Storing rendered SVG per concept, which is the 183-entry diagram corpus and is exactly what an interactive figure is not. Server-side parameter validation, for the duplication reason above. A single shared chunk for all six templates, which would ship five figures a learner never sees to save five requests.

**What this decision does not do.** It does not add a visualization to any concept that lacks one, does not change how a lesson advances, and does not make the corpus larger: the six shards that carry a visual are the same six concepts as before, now with an optional field. It also leaves the 183 static diagrams in place, untouched and still the right mechanism for a figure that explains rather than responds.
