# ADR-062: A matrix figure is dragged, not performed

*2026-11-19*

**The matrix figure is an instrument first and a playback second.** A learner edits `A` by dragging either column arrow, or by typing a coefficient, and the plane, the shaded unit-square image, the column combination and every readout follow from the same four numbers. The animation exists because a transformation is a process, but it is opt-in: nothing schedules a frame until Play is pressed, and the direct gesture remains the primary way to change the picture. The production template compiles to a **24,022-byte lazy chunk, 8,710 bytes gzip**, renders **1,417 px tall at 1280, 1,456 px at 768 and 1,595 px at 320**, and reports `scrollWidth − clientWidth = 0` at all three widths.

**Dragging a column and typing a coefficient are the same edit.** In the previous figure the two arrows were outputs: four number fields changed the matrix, and the arrows redrew. But the columns of `A` *are* the images of the basis vectors, so the arrowhead is not a picture of the number, it is the number drawn. Both gestures therefore write the same state through one `editMatrix` call, and neither can disagree with the other. A drag clamps to ±2 and rounds to one decimal so the readout stays legible; a grab must land within 0.42 data units (about 23 px here) of a knob, and empty space is not a grab, because the prototype's habit of throwing `v` at any stray click made every mis-click an edit. The pointer halo appears only under the pointer, which is what tells a learner which of two nearby knobs is about to move.

**The picture states only what the arithmetic can support.** `columns` is derived through `apply`, so the arrow drawn for `A e₁` is the first column by construction rather than by a second calculation that could drift. The shaded quadrilateral has vertices `0`, `A e₁`, `A(e₁ + e₂)`, `A e₂`, so its area is `|det A|`, and the sign of the determinant is named as orientation preserved, reversed or collapsed. `A⁻¹` is reported exactly when the determinant is nonzero, and a singular matrix says `no inverse (singular)`. Composition is preserved: when a second matrix `B` is authored, the readout keeps `BA`, `BAv`, `det BA`, `|Av|` and `|BAv|` distinct, because `A` and the composed map are different facts. The old figure's traversal arrows, its `A⁻¹Av = v` ring and its axis ticks are gone: they lengthened the readout without adding a fact a learner could act on. The inverse itself returned after the compact revision dropped it, because it was the answer to the lesson's own question about invertibility.

**The animation interpolates the matrix, not the drawing.** `M(t) = (1 − t)I + tA`, entry by entry. Every intermediate `M(t)` is itself a matrix, so every frame is a real linear map of the plane; a cross-fade between two pictures would show two images and call the blend a third. While the plane is drawn at `M(t)`, `A`'s own columns stay put as the destination and the readout stays `A`, so the moving grid is always compared against the matrix it is heading for. Only two places mention the intermediate: the label on the moving image (`M(t)v`) and the state chip (`M(t), t = 0.19`). One `requestAnimationFrame` loop is owned by one effect, and its cleanup cancels the frame on pause, completion, matrix edit, preset choice and unmount. Editing `A` stops playback and returns to `A` because an edit is a statement about the destination; editing `v` does not stop it, because moving the thing being transformed is worth watching mid-flight. Scrubbing cancels playback and sets the time directly, Show A returns to the endpoint without playing, and `prefers-reduced-motion` never schedules a frame at all: Play sets `t = 1`, clears the playing state and leaves the scrubber as the way to inspect `M(t)`.

**Four collapse states, because three different facts were sharing one word.** A determinant of exactly zero, a determinant that is tiny relative to the entries and an image whose thinnest dimension is below a pixel are not the same statement, and only the first is singular. `collapseState(m, pxPerUnit)` therefore separates `singular` (`scale = 0` or `|det| ≤ 1e-10 · max|entry|²`), `pixel` (parallelogram height under 0.5 px at the current scale), `near` (`|det| ≤ 1e-3 · max|entry|²`) and `none`. The classification is a drawing verdict, and the readout keeps the mathematical one beside it: a matrix `diag(1, 0.005)` at the figure's 41.9 px per unit is 0.21 px high, prints `thinner than a pixel, det = 5.0e-3`, and still prints `A⁻¹ = [[1,0],[0,200]]`. A rendering observation is never allowed to become an invertibility claim. Determinants and areas below 0.01 also print four decimals, so a thin matrix does not round to `0` beside a finite inverse.

**Labels are placed, not guessed.** A fixed offset per arrow is what drew `Av` through `A e₁` when the arrows pointed the same way and pushed labels through the frame edge at 320. `placeLabels` tries a short list of offsets around each tip, including candidates behind the tip for the case where the only free room is inside the frame, and takes the first that stays inside the padded plot and clear of every label already placed and every knob. It is pure, deterministic and tested without a DOM. A column that already is a basis vector gets no `A e₁` label, so the start of an animation does not show two names on one arrow. Labels are SVG text with a background-colored halo, which keeps them readable where they cross a grid line.

**Accessibility is carried by the same numbers the drawing uses.** The plane is `role="img"` with an aria-label naming what can be dragged. `MatrixBox` states the whole matrix in its aria-label, because the `A e₁` and `A e₂` footers are not a sentence. Coefficients are native number inputs labeled `a`, `b`, `c`, `d`, `vx`, `vy`; `t` is a range with a stepped number box; presets are a native select; every control answers the keyboard. Nothing depends on color alone: orientation is a word, the second column is dashed as well as orange, and the collapse state is spoken. The figure uses no emoji, only text and typographic arrows.

**The prototype was measured, promoted and deleted.** The approved prototype lived at `app/prototransform/` with `prototypes/TransformLab.tsx`, `prototypes/TransformPrototype.tsx`, `prototypes/transformMath.ts` and `public/prototype-review/`. All of them are removed, a repository-wide search finds no references, and the unrelated `prototypes/project.ts` and solid-renderer prototypes are untouched. Two conflicts were resolved rather than papered over. The owner had earlier rejected an automatic tween, so the animation is opt-in and secondary while drag-to-edit stays primary. `MatrixBox` was specified as display-only, so editing stays in the existing number fields plus the drag, and the matrix box only states the current state. The authored shard's three-option prediction was reduced to two and its caption rewritten to describe the columns, the area and the inverse condition, because the approved layout has a two-option prediction and the old caption described the figure that was replaced. Both shard edits were concrete requirements of the design, not incidental drift. The plot window was raised from the prototype's ±2.4 to ±3.2 because the authored `Av = (3, 2.2)` was clipped and the figure's own note read "an arrow leaves the window"; drags still clamp to ±2, so the extra window is not slack a learner feels.

**Verification was run against the production path, not only the component.** The full Vitest suite passes (**164 files, 1,411 tests**), including 16 tests for this figure, 5 for label placement and 10 new matrix-helper tests covering endpoints and midpoint, columns versus `apply`, the column combination, singular and projection matrices, determinant, area and orientation, quarter-turn and reflection interpolation, the four collapse states, inverse availability and reduced motion. `tsc --noEmit` is clean, lint reports 0 errors and 6 pre-existing warnings, the Go lesson and server tests pass, `make validate` passes and the static export builds. Two browser tests now mount the tangent and matrix figures through the real dispatcher, registry and lazy chunk at chromium, mobile-chromium and mobile-320 width, and all six executions pass. A separate probe confirmed Play → Pause → `M(t), t = 0.19` → back to `Av` with `A`'s readout byte-identical, zero label overlaps at 1280 and 768, and no console errors; the 320 console errors reproduce identically on an unrelated figure, so they are pre-existing.

**Known limitations, recorded rather than hidden.** The window is ±3.2 while a drag clamps to ±2, so a typed entry can reach a place a drag cannot; that asymmetry is a deliberate guard against losing a knob off-screen, not an invariant. Label widths are estimated at 6.9 px per character, and the collision test uses the same estimate, so the tests prove the placement rule is consistent rather than that real glyph metrics never collide. The interpolation is linear in the entries, which means a reflection passes through a singular matrix halfway; that is a true fact about this path and not a claim that every path between two invertible matrices is invertible. The figure is 1,595 px tall at 320 px wide by decision: the plot and the prediction block were not shrunk to chase a shorter card, and the readout, the four coefficient fields, the `t` slider and the challenge list are all still there. The inverse is printed without spaces (`[[1,-1],[-1,2]]`) because the spaced form wrapped to three lines in a 320 px cell, which costs a little readability.

**What this does not do.** It adds no dependency and no second matrix engine. It does not change `FigureFrame` or any unrelated template, and it does not move any registry, allowlist or coverage file. The only shard edit is the prediction and caption of `linalg.matrix.mult`, made because the approved interaction replaced the three-option block and the old caption described the old drawing. Nothing is pushed, merged or changed on `main`.
