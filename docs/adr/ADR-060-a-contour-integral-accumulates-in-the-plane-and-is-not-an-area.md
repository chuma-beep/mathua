# ADR-060: A contour integral accumulates in the plane, and it is not an area

*2026-11-18*

**The figure a learner needs here is not a graph of a function under a curve.** For a real integral, shading the region between the curve and the axis is the right picture because the value *is* that area. A complex line integral is a different object: it takes complex values, it depends on the path as well as the endpoints, and it is not the area of anything. So the figure draws the path in the z-plane, the image of that path under f in the w-plane, and the running value `I(t) = ∫_{C[0,t]} f(z) dz` as a vector from the origin in the w-plane, with its endpoint tracing a curve as the parameter advances. Nothing is shaded. A learner who has just met the real definite integral will look for an area, and the honest answer is that there is none to look for; the accumulation happens in a second plane.

**There are two frames and they are deliberately independent.** The z-plane is scaled to the path, and the w-plane to the values, because on the unit circle `|f(z)| = 1` while `|I(t)|` climbs to `2π` — common scaling would shrink the path to a dot or push the accumulation off the plot. Each panel computes its own extent from what it draws, with a floor so a small path is still legible, and the accumulated value sets a cap so a nearly constant function does not magnify numerical noise into a dramatic curve. The two frames are not a stylistic choice and are not negotiable: the first prototype attempt at a shared scale drew a path of radius 1 and an integral of magnitude 6.28 in a box sized for the larger, which made the path unreadable.

**Every path is a function of one real parameter, and reversing the path negates the integral.** The closed family is a segment, a circle, an ellipse and a wavy closed curve, each with a `pathAt(path, direction, t)` returning both the point and its derivative, so the drawing and the quadrature use one definition. Direction folds into the parameter as `s = direction === 1 ? t : 1 - t`, which makes reversal a change of sign in `ds` rather than a second code path. The midpoint rule over that parameter, with 2000 samples, reproduces every analytic value the tests assert to better than `1e-7`: `∮ 1/z dz = 2πi` on the unit circle, `−2πi` when traversed the other way, `0` for `z`, `z²` and `e^z` on any closed path, `2πi r²` for `conj z` on a circle of radius r, and `2πi` for `1/z` on a circle that does not enclose the origin is `0`. The contrast the lesson is built around is `2πi` against `0` for the same path with different functions.

**A pole on the path is reported, never averaged over.** A midpoint rule can step over a singularity and return a large finite number for a divergent integral, which is worse than a wrong answer because it looks like an answer. The first prototype did exactly that for a line from (−1, −1) to (1, 1) through the origin: 2000 samples of `1/z` along that segment summed to a plausible magnitude. Detection is therefore geometric rather than numerical, and it is exact wherever the geometry allows it. A segment is an exact point-to-segment distance. A circle is `| |center| − r |`, because the pole lies on the circle exactly when the center's distance from the origin equals the radius, so nothing is sampled. An ellipse and a wavy closed curve have no such closed form, so the distance is minimised numerically: a coarse sample brackets each local minimum, and 120 golden-section iterations refine the bracket on the interval around it. The samples only choose the intervals; they never decide the verdict, which is why a crossing that falls between two samples is still found. The crossing threshold is `1e-9`, and it is deliberately not widened: a path passing `1e-4` from the pole is a near miss and is reported as one, with `closest` printed in exponential notation rather than rounded to `0` beside a `clear` verdict. `poleInfo` therefore returns a `certainty` beside the distance, `exact` for the line and the circle, `converged` when a bracket narrowed below `1e-9`, and `uncertain` when none did, in which case the figure reads `unverified` rather than `clear`. A converged minimum is numerical evidence, not a proof: the bracket test does catch a tangential touch, which a sign change in the distance's derivative alone would miss, but a path whose excursion is narrower than the sample spacing could still evade it. Where detection fires it names the crossing and refuses to report a number: the readout shows `undefined`, the accumulation vector and trace are omitted, and the image curve is dimmed rather than drawn at full strength, so the state cannot be read as "the integral equals that curve".

**The accumulation is shown as a vector plus a trace, and the trace is supplementary.** The vector from the origin to `I(t)` is the current value; the lighter curve through earlier partial sums shows the route it took, which is what makes the final result feel earned rather than asserted. Neither replaces the other: a vector alone hides that the accumulation can loop back, and a trace alone hides where the value is now. The readout reports `I(t)` with a real and an imaginary part, its modulus and the total at `t = 1`, so a screen reader gets the same facts as the drawing.

**The prototype was measured before the template was written, and the numbers are prototype measurements.** In Node 24 with type stripping, 200 full accumulations of `1/z` on the unit circle took 0.345 ms at 200 samples, 0.362 ms at 1000 and 0.456 ms at 2000, with the imaginary part at 6.283185 in each case. In headless Chromium the numerical core at 2000 samples took a median of about 0.6 ms (0.4–2.9 ms including first-call warm-up), a progress step including the React commit took 6.9 ms on average and 8.4 ms at worst, and changing the path or the function took 4.3–6.0 ms. The module gzips to 2,257 bytes before minification. These are measurements of a prototype on a developer machine, evidence for the design, not production performance guarantees; the production template adds React rendering, controls and a second panel, and a first visit also pays its chunk download.

**No 3D dependency is involved, and the implementation is deliberately separate from `ComplexMapping`.** A contour is two-dimensional data drawn in two dimensions, so this uses the same SVG approach as the other 2D templates and loads as its own small chunk; nothing here imports Three.js. The earlier complex-mapping figure shows what a map does to angles at a point and the level-curves figure shows where a function is real or imaginary. Neither accumulates anything along a path, and folding this into either would have produced a figure with two unrelated interactions and one caption. The curriculum home is `complex.integral.contour`, whose first step is already "integral of one over z around the unit circle".

**What this does not do.** It does not compute residues or winding numbers, does not draw the image of the interior, and does not promise singularity detection beyond the geometry it states: exact for a segment and a circle, converged rather than proved for an ellipse and a wavy curve, and explicitly unverified when the minimiser fails to bracket a minimum. It offers five functions and four paths rather than a general expression parser, for the same reason the Riemann figure takes polynomial coefficients: a closed set can be tested against closed-form values, and a parser cannot. Coverage for contour integration stays partial after this work, because the figure demonstrates the idea on a small family of paths and functions rather than a general theory.
