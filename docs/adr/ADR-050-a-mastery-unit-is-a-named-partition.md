# ADR-050: A mastery unit is a named partition of the existing DAG, and a pass adds evidence without setting mastery

*2026-10-07*

**The decision.** Four things, in dependency order. **A mastery unit is a named partition of the existing DAG, never a second hierarchy.** `data/mastery_units.json` is new authored data, but membership is the only thing it authors: `prerequisiteUnitIds` is **not authored at all**, it is derived from the concept DAG's closure over each unit's own members. That is a correction to the spec as first written, which proposed authoring both, two authored hierarchies that can contradict each other, and validate_graph only knows about concepts. Deriving it removes the contradiction at the source rather than adding a reconciliation check, and it preserves the branching prerequisite structure for free: units inherit a DAG, so A can unlock B and C independently while D waits. **Passing adds evidence; it never sets mastery.** `unit.status = mastered` is *derived* from all member concepts reaching `mastery.StatusMastered` by the existing ladder (`mastery.MasteryThreshold 0.6`, `MasteryEvidenceFloor 6`). The alternative, the assessment writing status directly, was chosen against: it makes two things called mastery that can disagree, and `mastery.MasteryPct` exists precisely on the premise that the tier *is* attainment. The honest consequence, recorded rather than hidden: **a pass does not guarantee progression.** A learner who misses every question on a unit's assessment stays blocked, because the evidence says so. That is the reading of "the assessment verifies it" that does not require believing the test. **Two states are stored, five are derived.** Only `assessment_required` and `remediation_required` cannot be computed from `concept_progress` plus the assessment record; `locked`/`available`/`learning`/`assessment_ready`/`mastered` are functions of the DAG and existing state. Seven manually-maintained statuses would be seven ways to disagree with the ladder. **`Engine.ProgressionGate(studentID)` is the single server-side answer to "can this learner progress, and if not, what must they do?"** Invariants that UI cannot enforce have to have exactly one implementation, or they get enforced inconsistently and the inconsistency is the bypass. It is called by `RecommendNext`, `NextQuestion` and the practice endpoint; Study, Graph, History and Settings never call it, which satisfies "reference access remains available" structurally rather than by policy.

**What is being rejected, and why.** A second graph: ADR-001 fixed `Concept` as the atomic node and ADR-019 kept destinations derived from prerequisite closures specifically so "graph stays source of truth"; a second authored hierarchy reopens the question this repo closed twice. A second mastery writer: ADR-037/038 locked mastery as an exit decided by evidence and ADR-039 found a *single* graded-attempt authority after a difficulty bug hid in a path that re-derived its own number, a second writer is how that recurs. Seven stored statuses: see above. A per-concept quiz: the boundary is a unit, so a learner is not tested after every concept, which is the whole point of a partition.

**Invariant placement**, since the requirement is that these are tested rather than intended: the partition rules live in `concepts.Build` (`internal/concepts/loader.go:126`), next to the existing cycle and orphan checks, because `make validate` already runs `scripts/validate_graph.go` first and would otherwise need a second gate. `ProgressionGate` is the only implementation of the boundary, and invariants 1/7/8/10 assert that `/api/next`, `NextQuestion` and the practice endpoint all route through it, a test that constructs `/learn?concept=...` directly and expects refusal is the only honest form of invariant 8, since anything else tests the UI. Assessment pass/fail and remediation live in the new table; invariants 4/5/6 are table-level state-transition tests. Invariant 2 (a refresh does not clear it) and 3 (it survives navigation) are properties of storing the requirement at all rather than in client state, and are asserted against a fresh engine instance so they cannot pass by accident.

**Deferred and named rather than quietly assumed.** The pass threshold, the assessment-readiness heuristic, the remediation quantity before retake, and the authoring of 1476 concepts across units are **four undecided things that the decision map carries**, they are not settled by this ADR and no migration should be written before they are. A unit of one concept is permitted by the partition rules but should be a content error, and the authoring pass is where that gets caught rather than a schema rule. Retention/spacing across the assessment boundary is still ADR-037's open `tier_attained_at` question and is unchanged by any of this.

**Amended 2026-10-07, the draft partition exists and it says the rule does not work.** `data/mastery_units.json` is a generated width-3 draft: **136 units, all 1476 concepts covered exactly once**, no authored prerequisite edges (the file cannot express them; `TestMasteryUnitFile_StoresNoPrerequisiteGraph` fails if a `prerequisiteUnitIds` key appears), band width recorded in the data rather than in a constant so regeneration is `go run ./cmd/masteryunits -band N` and not a code change. Three findings and the first is a retraction. **I published a wrong measurement.** "32 units, 22 backward edges, condensation depth 13, 0 unresolved" came from a Kahn's algorithm that enqueued a node when it was first seen rather than when its in-degree reached zero, which processes a node before its predecessors and silently "resolves" cycles, the `0 unresolved` was the tell and it read as success. The Go implementation initially made it worse: a missing map entry reads as `0`, so 26 cyclic subdomains were banded as foundations, giving 36 units and 96 backward edges. **A confidently wrong answer rather than a missing one**, which is precisely what this ADR exists to prevent, committed by the same author in the same week. `SubdomainDepths` now returns its unresolved set and callers cannot ignore it. **The 22 backward edges were never a property of the corpus**, under concept depth there are zero at every width from 1 to 45, by construction. **Subdomain depth does not exist for 60 of 125 subdomains, 26 inside condensation cycles and 34 downstream of them, and domain depth for 14 of 17**: grouping loses the DAG's acyclicity, so `abstract_algebra.{fields,groups,rings,structures}` and `calculus.{advanced,derivatives,integrals,limits}` are cycles at subdomain level. Concept depth is the only well-defined function (1476/1476, max 44). **And no band width is clean**: width 2 gives 22 singletons and width 3 gives 19, which is a quiz per concept and is what §12 forbids; width 45 is just the 17 domains with calculus at 128 concepts, which is not assessable. So the honest D3 result is that *derivation alone does not produce assessment-grade boundaries*, which makes the authoring decision larger, not smaller. The width is still reversible; the band is in the data.
